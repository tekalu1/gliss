# ガイド対応の網羅率と表示案（issue #53）

## 調査条件と測定方法

- 2026-09-27、`guide-coverage` のコードで測定。手元の曲 T（約 165 秒）の `project.json` と解析キャッシュ、158 秒の曲の同等ファイルを `%TEMP%/gliss-guide-coverage/` にコピーした。C/C2 はテスト素材（`docs/testing.md`）の音声から同ディレクトリに新規プロジェクトを作った。元のプロジェクト・WAV・SVP は読み取りだけ。出力 JSON も `%TEMP%/gliss-guide-coverage/result.json` に置く。
- 分母は解析済みテイクの `kind="note"`（音程ノート）。**音程対応**は `timing.note_correspondence()` の `pitch_target`、**タイミング対応**は `guide_timing.of_project()` の発音の頭の組がそのノート内にあるかで別々に数えた。後者はノートの前 60 ms、後 20 ms までをそのノートに含める。実際の計画の `timing_notes` も併記した。
- 精度の代理指標は **別方式の 3 帯域エネルギー立ち上がり**（`engine/tests/onsets_ref.py`）をテイクとガイドに適用して得た組の残差。各候補が提案する頭の移動をその頭の近傍 ±80 ms に仮適用した値で、製品の伸縮・接続・到達制限を再現していない。組の作成は既存 DTW を位置の手掛かりとして共有するため、手注釈の正解率ではない。改善候補を同じ 87 / 8 / 30 組で比較するスクリーニングである。
- `plan_guide()` が返した対応グループ数、補正対象の頭と実際に目標へ届く頭も確認した。音程対応ありは「タイミングも直る」を意味しない。

## 対応できない理由

発音の頭を組めないノートの内訳。理由はノートごとに優先順位を付けて一つだけ記録した診断で、音の有無の厳密な手注釈ではない。各ノートの時刻は手元の記録にだけ残した（曲の中身に結び付くため）。

| 主な診断 | 曲 T | C/C2 | 158 秒 |
|---|---:|---:|---:|
| テイクの発音の頭を検出できない | 44 | 4 | 11 |
| 対応ガイド内で発音の頭を検出できない | 12 | 1 | 5 |
| DTW で写した位置の近くにガイドの頭が無い | 4 | 0 | 11 |
| DTW の写像が揺れる・全体のずれが定まらない・外れた組 | 1 | 1 | 11 |
| 1 対多・候補が曖昧・隣の頭との取り違え | 11 | 4 | 3 |
| 音程ノートの相手が無い | 1 | 0 | 0 |
| タイミング対応あり | 38 | 4 | 0 |

曲 T の「発音の頭はあるが一対一の組が無い」11 件は上表の曖昧欄に含めた。158 秒の曲は別演奏の箇所が長く、単に距離のしきい値を広げても 1 対多や誤った節を増やす。音程ノートに立ち上がりが無い場合には、音程だけの区切りをタイミング補正の単位として扱うべきではない。

## 表示案の比較

比較には単一 HTML のモック（素材の画面を埋め込んでいたので公開リポジトリには入れていない）を使った。承認済み v4 の配色・既存ポップアップを基礎にした**概念図**で、重ねた線と未対応印の位置は実測ノートではない。

| 案 | いつ出すか | 利点 | 難点 |
|---|---|---|---|
| A | 常時 | 全体の流れを追える | 長いフレーズで線が密集し、音程・補正の線を隠す |
| B | 選択・ホバー中だけ | 編集画面を静かに保つ | 未対応に選ぶまで気付けない |
| **C** | **「ガイドに合わせる」を開いている間、選択範囲だけ** | **補正直前に対応と未対応を同時に確認できる** | 範囲が広いと線が増えるため拡大率で間引きが要る |

**推奨 C**。対応が確かな組だけ細い中立の灰色線を引き、音程のみの対応とタイミングの頭の対応はツールチップの語で区別する。未対応には灰色の破線印を付ける。1 対多は組の範囲を示し、一本ごとの一対一であるかのように描かない。ガイドは暗い灰色、補正量は黄から赤、手動は白という既存の意味を維持し、装飾的な枠や新色を足さない。表示には計画が返す `pairs` と `timing`、到達可否を使い、対応が無い理由を読めるようにする。

## 推奨案と実装に向けた判断

**アルゴリズムの推奨は、発音の頭を先に確定し、信頼できるノート対応の内部だけで追加候補を探す二段構え。ただし現時点では追加候補を自動適用しない。** この順序なら既存の高信頼な 1 対 1 の組を維持し、音程ノートで探索範囲を限定できる。一方、今回の無条件な二段構えは C/C2 で 4/14→7/14 と増えたが、別検出の中央値が 37.5→97.2 ms、悪化が 0→5 件。曲 T と 158 秒でも精度非劣化を示せなかった。実装前に、候補の相互最近傍・曲中の局所的な時間基準・音節または別音響特徴による合意を条件として追加し、同じ検査で再測定する。

したがって**今回確認できた精度維持下の網羅率見込みは、曲 T 38/111、C/C2 4/14、158 秒 0/41 から増分 0**。特に 158 秒の曲に「41/41 対応」と表示するのは誤解を招く。まず表示で実際に補正できる箇所を明確にし、アルゴリズムの採用条件は「全素材で別検出の悪化数と 90% 残差を増やさず、対応ノート数を増やす」にする。見込みを上回る数値は今回のデータからは保証できない。

## 実装: 基準点と補間（issue #53 の対応）

調査の後、承認された方針で実装した。

### 方式

- **基準点**: 今の `guide_timing` の高信頼な 1 対 1 の発音の頭の組（と、それと一緒に動くノートの頭）だけ。推定の読み（#52）は基準点にしない。テイク・ガイドとも**確定の**歌詞がある所では、休みの手前の音節の終わり（母音の尻）もガイドの音節の終わりへの基準点にする（`timing.py: _syllable_end_pairs`）。子音と母音の境目は使わない（子音は長さを保つので、音節の頭と別の目標を付けると伸び縮みできない）。
- **補間**: まず以前の規則（隙間を挟まない両隣の基準点の間を比例、片側だけなら同じノートの尻を同じだけ）。残った頭・尻は、同じフレーズ（0.5 秒以上の隙間で区切る）の基準点を今の時刻で結んだ折れ線の値へ（`_interp_targets`。VocAlign と同じく区間を隙間ごと連続して伸び縮みさせる。隙間の中身は元の位置のまま端だけ動く）。フレーズの端の基準点より外は、その基準点と同じだけ平行に。**前後の基準点の間が 1 秒を超える所**（端の外なら基準点から 1 秒より遠い所）と、基準点が 1 つも無いフレーズは動かさない。補間の目標は「ゆずれる目標」で、追い越し・短すぎになるときは先に戻す。
- 計画の仕組みはそのままなので、スライダー中のプレビュー（`cur + d·x`）と確定が同じ計画を使い、取り消しは 1 回で戻る。
- 計画にノートごとの対応 `notes`（音程の組・確かな組か・音程が寄るか・タイミング = 基準点 / 補間 / なし・100% で届くか・理由）を載せ、画面と MCP（`plan_edit` / `correct_to_guide` の `correspondence`・`timing_possible`）で同じ中身を返す。

### 採用の条件の検査（前後）

手元の計測スクリプト（素材に結び付くので公開リポジトリには入れていない）で、各素材の**元の状態**（コピーで編集を全部取り消した状態）に全体・タイミング 100% の実際の計画を当て、別方式（3 帯域エネルギー立ち上がり）の組で測った（悪化 = 絶対残差が 10 ms 以上増えた組）。「前」は origin/main と同じ計画（`interpolate=False`・音節の終わりなし。曲 T・C・C-lyrics で `plan.d` が main の計画と完全に一致することを確かめた）。**タイミング補正の対象ノート = 頭に目標（基準点か補間）が付いた音程ノート**。以前の規則もつながったノートの間は比例で動かしていたので、調査の「発音の頭の組があるノート」（38/111 など）より多い。

| 素材 | 対象ノート 前 → 後 | 基準点 / 補間（後） | 100% で届く（後） | 別検出の組 | 補正前 中央 / 90% (ms) | 補正後 中央 / 90% 前 → 後 (ms) | 悪化 前 → 後 | 改善 前 → 後 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 曲 T のコピー | 96 → **98** / 111 | 45 / 53 | 98 | 87 | 20.0 / 64.9 | 14.6 / 83.2 → 14.7 / 83.3 | 20 → 20 | 24 → 24 |
| C / C2 | 8 → **14** / 14 | 5 / 9 | 14 | 8 | 59.9 / 145.2 | 44.4 / 133.3 → **41.4 / 120.9** | 2 → **0** | 5 → 4 |
| 158 秒の曲 | 0 → 0 / 41 | 0 / 0 | 0 | 30 | 32.4 / 94.3 | 32.4 / 94.3 → 32.4 / 94.3 | 0 → 0 | 0 → 0 |
| （参考）C / C2 に両方の確定の歌詞 | 12 → 14 / 14 | 11 / 3 | 14 | 8 | 59.9 / 145.2 | 89.4 / 226.4 → 90.8 / 172.8 | 5 → 5 | 2 → 2 |

満たせなかった所と理由:

- **曲 T の 90% 残差 83.2 → 83.3 ms（+0.1）・中央値 14.6 → 14.7 ms**: 動きが変わった組は 5 つで、**全部が同じか改善**（n045 7.3→6.2、n084 39.4→34.9、n129 49.8→44.9、n131 19.9→18.1、n148 12.2→4.9 ms）。悪化した組は無い。+0.1 ms は、測り方が補正後の組から全体のずれ（基準）を推定し直すためで、改善した組が基準を約 0.05 ms 動かし、残りの組が一様に 0.1 ms 以内ずれた分（丸めの境目）。組ごとの比較では悪化していないので採用したが、条件の文言（90% 残差を増やさない）には 0.1 ms 届かない。
- **158 秒の曲は対象ノートが増えない**: 確かな頭の組（基準点）が 1 つも無い（別の演奏で、ガイドと長さも違う）。方針どおり基準点の無い区間は動かさない。代わりに画面のステータス行と MCP の `timing_message` で「このガイドとはタイミングを合わせられない」と出す。
- （参考）C / C2 に両方の歌詞を入れた場合は、以前から補正後が補正前より悪い（音節の組の問題。今回の範囲外）。補間で 90% 残差は 226.4 → 172.8 ms に下がり、悪化数は同じ。音節の終わりの基準点は 1 ノート増えたが、別検出は立ち上がりしか測らないので、この表では効き目が出ない。

**中身の違うガイドでの注意**: テイク C に別の歌を重ねると、確かな頭の組はたまたま 0〜2 個できる。素材 E では 2 組で、以前は 5/14、補間で 14/14 ノートに目標が付く（動く量の最大は 32 ms のまま。補間は基準点の目標の間の値しか取らない）。素材 D 4→8、H・A 2→6（動く量 0 ms）。W・G は 0 組で動かない。「フレーズに基準点が 2 つ以上」で防げるが C/C2 の改善（8→14）がほぼ消える（9）ので採らなかった。画面のホバーとステータス行で「補間」の数と理由が見えるので、少ない基準点に引かれている所は確かめられる。

### 表示（案 C）の実装

「ガイドに合わせる」を開いている間だけ（計画が載っている間）、計画の対象ノート（選択、無ければ全体）について描く。確かな組（確かな頭の組で裏付けられた組。`pairs[].confirmed`）はテイクの頭とガイドの頭を細い灰色線と両端の小さな点で結び（ほぼ縦の線をガイドの線の段差と見分けるため）、1 対多は組の頭どうし・尻どうしの 2 本で範囲を示す。組の尻と次の組の頭が同じ所に来るときは 1 本にまとめる。確かな組の無いノートは灰色の破線の丸。色は既存の灰色（選んだノートの元の長さの線 `#a4a4aa`）だけで、新しい色・枠は足していない。線は帯の上・テイクの曲線の下。縮小して線の両端とも 6 px 以内・丸の中心が 14 px 以内に並ぶものは間引く。ノートにポインタを乗せると、1 行目に「音程だけ対応／タイミングも対応（基準点・補間）／タイミングだけ対応／対応なし（直らない）」と「目標に届く／届かない」、2 行目以降にガイドのノート（1 対多なら範囲）と理由。ステータス行には「ガイドとの対応: 確か 9/14 ノート・タイミング 14/14（基準点 5・補間 9）」、確かな頭の組が無いガイドでは「このガイドとはタイミングを合わせられない（確かな発音の頭の組が無い）」。テストは `app/tests/guide-coverage.spec.js`（撮った画面は `app/screenshots/`。git 管理外）。
